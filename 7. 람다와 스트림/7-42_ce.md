# 익명 클래스보다는 람다를 사용하라

- 이전에는 함수 객체에서 익명 클래스를 많이 사용했다.

```java
Collections.sort(word, new Comparator<String>() {
	public int compare(String s1, String s2) {
		return Integer.compare(s1.length(), s2.length());
	}
}
```

- Comparator: 정렬을 담당하는 추상 전략
- 익명 클래스: 정렬을 담당하는 구체적인 전략

익명 클래스 방식은 코드가 너무 길기 때문에 자바는 함수형 프로그래밍에 적합하지 않았다.
자바 8에 람다식이 도입되면서 코드를 훨씬 간결하게 바꿀 수 있게 되었다.

```java
// 익명 클래스를 대체 - 람다식을 함수 객체로 사용
Collections.sort(words, (s1, s2) -> Integer.compare(s1.length(), s2.length())));
```

- 람다에서는 매개변수의 반환값 타입이 명시되어 있지 않다. -> 컴파일러가 문맥을 통해 타입을 추론해준다.
- 상황에 따라 컴파일러가 타입을 결정하지 못 하는 경우에만 프로그래머가 직접 명시한다.
- 타입 추론 규칙은 복잡하기 때문에 타입을 명시해야 코드가 더 명확할 때 빼고는 람다의 모든 매개변수 타입은 생략할 것. 컴파일러가 오류를 내면 그때 타입을 명시해주면 된다.

```java
// 비교자 생성 메서드 사용
Collections.sort(words, comparingInt(String::length));

// 더 간략화
words.sort(comparingInt(String::length));
```

```java

	PLUS(“+”, (x, y) -> x + y),

```

- apply 메서드에서 람다를 호출

### 정리

- 람다는 이름도 없고 문서화도 못 하기 때문에 코드 자체로 동작이 명확하기 않거나 코드 줄 수가 많아지면 람다를 사용하지 않는 것이 좋다.
- 람다는 한 줄이 가장 좋고 길어도 세 줄이어야 한다.
- 람다가 길어지고 읽기 어려워진다면 람다를 쓰지 않는 쪽으로 리팩토리하자.
